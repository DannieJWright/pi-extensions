# Orchestrator workflow

Use only when the user directly requests orchestration of ledger work. Do not implement items, conduct reviews, or run validation yourself. Run one delegate at a time; claims do not lock the ledger and parallel writers or shared-workspace work are unsupported.

## Setup

Ask for the ledger path if the user did not supply it; do not choose a default for them. Resolve it to an absolute path against the original session root and pin both values for every prompt and ledger call. Read state through tools, not by opening or editing the live ledger. Call `ledger_check` with the path and stop on problems. Call `ledger_orchestrate` with `action: list` once to inspect state. If any required ledger or delegation tool is unavailable, stop and report the missing tool and role. Bundled pi-subagents worker/reviewer tool access and reviewer write permission are an external dependency being addressed separately; do not configure overrides here.

## Sequential loop

1. Call `ledger_orchestrate` with `action: next` and the pinned path. If nothing is selected, call `action: list` and report accurately whether all items are done, any are assigned/in flight, any are capped, or work is otherwise blocked. Never equate no selection with completion. Surface open findings, failed counts and effective cap/config; at a cap stop or change configuration only when authorized by the user.
2. For `todo` or eligible `in-progress`, read `acceptance_criteria` from the `next` result. If any criterion contains the exact text `UI evidence required`, select `ui-worker` and use the agent ID `<feature-id>-<failed-reviews>-ui-worker`; no other text decides the route. Otherwise select the normal worker with `<feature-id>-<failed-reviews>-worker`. Do not call `ledger_work` start to route. For `review`, choose the reviewer. The deterministic assignment ID, `<feature-id>-<failed-reviews>-<worker|ui-worker|reviewer>`, is provided as `AGENT_ID`; it is the same on every resume, so one assignment always maps to one agent. Read `subagents/worker.md` or `subagents/reviewer.md`, substitute all placeholders with the actual item ID, path, original root and agent ID, and dispatch the prompt to the selected agent. The prompt directly instructs the delegate to read the corresponding workflow. Track its external run ID in session history, not in the ledger. Wait for that one run to finish.
3. Require exactly one valid JSON object with seven nonempty string fields: `item_id`, `outcome`, `known_state`, `tests`, `commit`, `warnings`, `blocker`. Reject malformed JSON, duplicate, missing, extra or empty fields, mismatched ID, or invalid outcomes. Stop if outcome is not `submitted`, blocker is not `none`, tests are absent or unknown, or warnings make item changes or commit inclusion uncertain. A worker success requires a known work commit and state `review` or `done`. A reviewer success requires state `in-progress` or `done`; its ledger commit may legitimately be `none` when the ledger is untracked, ignored, outside a repository, or already matches HEAD after the write, but not `unknown`.
4. Verify the delegate's result with `ledger_get_feature` for the same ID and pinned path: check status, assignment cleared, work commit history where applicable, findings and count/config. A reviewer metadata commit is not part of work history: verify it in the ledger repository's Git history when one is reported, and confirm the stated reason when none is reported. Stop on mismatch, failed tool or uncertainty. Report a failed review and its open findings/cap/config; if uncapped, loop to `next` for a worker fix, then review again. If capped, stop unless the user authorizes resolution. Preserve and surface warnings, including out-of-workspace or branch warnings. Repeat only after verified completion of the previous run.

## Interrupted runs and recovery

Never release a live run. If a delegate is blocked, fails or disappears, stop and inspect known state and its tracked run ID. Establish that the assigned run has actually stopped; inability to establish this means stop and report, not release. Use `ledger_get_feature` to obtain the current assignment's agent ID and claim token. Only after verifying those match the stopped run, call `ledger_orchestrate` action `release` with its exact `id`, `agent_id`, `claim_token` and pinned path. Release clears the claim only; it does not change item status. A later start obtains a fresh token. If the run may have committed or written state before failing, inspect Git HEAD, index and ledger state and reconcile before any release or retry; report uncertainty rather than guessing.
