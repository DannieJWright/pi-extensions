# Git tools

The tools available today are read-only inspection. A future group that can change files will use its own prefix (`git_w_*`) so a reader can tell which tools may write.

These tools inspect a Git repository chosen by the optional `dir` parameter when it is given, otherwise by upward discovery from the child session's working directory; either route can reach a linked worktree. They do not need `bash`. They are an inspection interface, **not an access-control boundary**: they can expose any repository contents and history the Pi process can read. Because `dir` has no path gate, that reach widens beyond the session subtree to any directory the Pi process can read. A permission-mode file-path rule that denies `read` does not apply to a Git tool; custom tools are gated by **tool name**, not their path arguments or `dir`. In permission modes only `bash` uses the permission-mode OS sandbox; these tools run outside it, subject to the Pi process's own OS permissions and any external process sandbox.

## Tools

All arguments are structured; unknown fields, arbitrary flags, shell strings, and Git pathspec magic are rejected or treated literally. `paths` is an optional array of up to 100 nonempty literal paths relative to the directory actually used (`dir`, or the session working directory when it is absent). Spaces and leading dashes are supported. Two relativity rules are separate behaviours: Git pathspecs resolve against the directory actually used, while `status --porcelain` output prints paths relative to the repository top level regardless of the run directory (measured on Git 2.53.0; `-c status.relative=true` and `=false` change nothing there, and `--no-relative` is not a valid option for `git status`). Non-repository directories are reported as errors under the resolution rules below, and Git still reports invalid paths as errors. Output is Git text; an empty diff is normal.

- `git_r_status {dir?}`: branch and working-tree/index status, including untracked files.
- `git_r_diff {mode?, from?, to?, paths?, dir?}`: `mode` is `unstaged` (default), `staged`, or `range`. The range requires `from` and `to`; it compares those commits directly, not a merge base. For example, `{ "mode": "range", "from": "main", "to": "feature", "paths": ["src/a file.ts", "-dash"] }`.
- `git_r_log {ref?, limit?, paths?, dir?}`: commit hashes and subjects, newest first; `limit` defaults to 20 and must be 1–100. Without a ref, Git uses HEAD. Example: `{ "ref": "main", "limit": 10 }`.
- `git_r_show {ref, paths?, dir?}`: one commit's metadata and patch; merge commits show changes relative to the first parent. Example: `{ "ref": "HEAD", "paths": ["src"] }`.

Refs accept simple commit hashes, branch and tag names, starting with an ASCII letter or digit and containing only letters, digits, `.`, `_`, `/`, or `-`. Git revision operators (including `~`, `^`, and `..`) are not accepted; resolve a commit to a hash or use its branch/tag name instead. Refs must resolve to commits. Invalid input, missing refs, Git failures, timeout, cancellation, and process-start errors are reported as errors. Output exceeding 64 KiB is marked truncated and the Git process is stopped; split a large inspection by path or commit. A truncated tool result is not an error: `isError` stays false and the truncation appears only through the notes and `details.truncated`, while a preflight check that hits the limit throws instead, including the repository-root check described below. Every Git invocation has a 10-second timeout (a range resolves two refs before its diff), and cancellation stops the current process. The output cap combines stdout and stderr. Git output control characters are stripped.

The extension invokes Git directly with argument arrays. It removes inherited `GIT_*` variables, disables system/global Git configuration, prompts, optional index locks, pagers, fsmonitor, external diff, textconv, lazy fetching, Git color and signature display. It requires a Git version supporting `--no-lazy-fetch`; older versions fail rather than fetching objects. Missing promisor objects are reported as errors. Status and unstaged diff refuse to run if any repository filter driver is configured, even if unrelated to the selected paths, rather than execute clean/process filters or silently show an inaccurate diff. They also refuse if the index contains any submodule, initialized or not: Git may inspect a dirty submodule using that submodule's own filters. The whole index is scanned incrementally with bounded memory, even from a subdirectory; scan errors, timeout, cancellation, malformed output, or excessive diagnostic output refuse the inspection. Staged and committed inspections remain available. This preflight assumes repository configuration and index are not changed concurrently; it is not a security boundary against a hostile concurrent writer. On POSIX cancellation and timeout kill the Git process group and close pipes; escaped descendants are not guaranteed to be terminated. On Windows only the direct process is killed, but pipe cleanup still bounds the tool response. Repository configuration and data are still read; this is not a general sandbox for untrusted repositories.

## Run directory and repository resolution

`dir` is optional on all four tools. Absolute paths are accepted; a relative value resolves against the session working directory. The resolved target must exist and be a directory. A value that is not a string, is empty, exceeds 4096 characters, or contains a NUL is rejected by the same rule as the other scalar arguments; a nonexistent target or a target that is not a directory is rejected too. Both are validation-stage rejections answered through the plain error path, so they carry no label and no header. There is no path gate and no `realpath()` containment comparison, so Windows prefix and case normalization is out of scope. The target itself may be a symlink that resolves to a directory; candidate children under it are never followed, which is why `lstat` is used on the target rather than its type being read through the link.

For every kind, one bounded `git rev-parse --show-toplevel` runs at the target before anything else, and its result is reused for the submodule index scan instead of a second call. Upward discovery wins over the candidate scan. Timeout, cancellation, spawn failure, or any non-zero exit is reported under `Could not locate repository root`; output exceeding the limit keeps its own wording (`Working-tree inspection refused: repository root check exceeded output limit.`) because a truncated-but-successful lookup proves Git did find a repository, and reporting "no repository found" there would be wrong. The fails-closed guard on the lookup's output shape (`Could not locate repository root: unexpected Git output`) throws, so it is answered through the plain catch path with no header and no candidates; the bracketed candidate block below is the shape of a failed lookup, not of every failure. When the lookup answers with `fatal: this operation must be run in a work tree`, bareness is confirmed with `git rev-parse --is-bare-repository` before that label is used; anything other than exactly `true` falls back to reporting the failed lookup as no repository found. Prefix derivation for the submodule scan compares the run directory against the physical top level, and the two views disagree when the target was reached through a symlink: measured on Git 2.53.0, `--show-toplevel` printed the physical path while `--show-cdup` printed `../` from the same run directory. So the prefix is derived only for a direct target and asked from Git otherwise; the derivations are not equivalent in all cases.

Nothing is auto-selected when nothing resolves. The caller gets an error that keeps Git's wording, names the parameter, and lists candidates, then re-issues with `dir`. Candidates are immediate children containing `.git` as a directory or file — depth is one level only, dotfiles count, symlinks are not followed, at most 50 entries are scanned (the cap counts every entry read, including skipped ones), all matching names are collected first, sorted byte-wise, and the first 20 are reported. Names come from `fs.readdir`, so they bypass control-character stripping; a name needing quotes is quoted rather than stripped, because stripping makes two different names collide. Detection costs no Git invocation, so each name is an unverified hint: a stale gitfile answers with `fatal: invalid gitfile format: <path>`, exit 128, when an inspection is run there. Inside the brackets the notes appear in `report()`'s fixed order: its own anomaly note for the failed lookup first, so a non-zero exit reads `Git failed (exit <code>).`, then the candidate note.

```
Could not locate repository root:
fatal: not a git repository (or any parent up to mount point /)
[Git failed (exit 128). No repository found from /tmp/plain-parent. Pass the "dir" parameter with a directory inside a Git repository or linked worktree. Candidates under this directory (immediate children only, at most 50 entries scanned, first 20 reported sorted byte-wise): aa-first, mm-middle, "multi\nline", zz-last. Some candidates may not resolve.]
```

When discovery succeeds, a guidance note is appended only if that repository has other registered worktrees. The main working tree never counts toward that trigger even though `git worktree list --porcelain` always prints it as the first record with no flag distinguishing it, so the note fires only when a record after the first is not the resolved checkout. Whether that is true cannot be known without asking Git, so this costs one invocation on every successful non-bare resolution, whether or not a note is appended. Records are counted as lines beginning `worktree ` with records separated by a blank line; later fields (`HEAD`, `branch`) do not start one. Only the `detached` flag was observed on Git 2.53.0 — `bare`, `locked`, and `prunable` were not produced, including for a worktree whose working tree had been deleted, where `git worktree prune --dry-run -v` printed nothing, so prunable behaviour is not asserted. A path containing a newline breaks record parsing: it is read as its first line only. The note lists at most 20 records, keeps porcelain order rather than sorting, states its own bounds instead of the tool output limit, marks the resolved checkout as the current repository, and says plainly that nothing was auto-selected. An anomalous answer on that optional call appends nothing and leaves the inspection successful. Example, in the form the tool produces:

```
Worktree guidance (20 records maximum, 81920 bytes of Git output maximum, this appended message is not bounded by the tool output limit): Records in git worktree list --porcelain order, which lists the main working tree first: /tmp/guidance-parent/zz-main (current repository, main working tree), /tmp/guidance-parent/aa-linked. Nothing was auto-selected; pass the "dir" parameter with a path from this list.
```

The header names the run directory and the repository top level whenever either differs from the caller working directory, compared after normalising so a trailing separator does not make a header appear where nothing differs. Otherwise the label stays plain and output is byte-for-byte what the same call produced before, except for an appended guidance note. When no top level resolves, only the run-directory part appears:

```
Git inspection (run directory /tmp/plain-parent/nested, repository /tmp/plain-parent):
Could not locate repository root (run directory /tmp/plain-parent/plain-child):
Git inspection (run directory /tmp/plain-parent/bare):
```

Measured behaviour in a bare repository: `log` and `show` work unchanged, because refs and objects can still be read there; `status` and unstaged `diff` fail with `fatal: this operation must be run in a work tree`, exit 128. There is no top level to print, so such a header shows only the run directory. `ls-files --stage` returns empty output with exit 0 there, which cannot be read as success, so the submodule scan is skipped for the kinds that would otherwise run it.

Worst-case wall time roughly doubles because every invocation keeps its own 10-second timeout. The counts below are the base path only — the single discovery lookup plus the kind's own work: status or unstaged diff goes from three invocations to four, `show` from two to three, and a range diff from three to four. They exclude the guidance check, which is paid on every successful non-bare resolution whether or not a note is appended, since applicability cannot be decided without asking Git, so the ordinary case is two extra invocations per call rather than one: five for status or unstaged diff, four for `show`, five for a range diff. A symlinked target costs one more for the prefix fallback, and a failed lookup followed by a bare confirmation costs one more; that confirmation is gated on the work-tree fatal so ordinary calls do not pay for it.

Windows symlink privileges were **not** verified here; Linux gives no evidence either way, and they remain an open limitation until checked on a Windows host.

## Agent setup and limits

The package registers the extension for normal Pi sessions. For another agent, preserve its existing tool allowlist and add `git_r_diff`, `git_r_status`, `git_r_log`, and `git_r_show`; do not add `bash` if the agent should have no shell. A named tool must have its provider loaded too. Foreground children do not inherit ambient extensions: list the provider's absolute `extensions/git-tools/index.ts` path in `subagentOnlyExtensions` (or `extensions`). Background children normally load ambient extensions; explicit `extensions` changes ambient loading. Agent/project overrides can replace the tool list or loading settings, and permission modes or child capability ceilings can deny a tool or extension. Test the effective configuration in each environment; acceptance roles and prompts are not security controls.

Project overrides win field by field over user overrides. The installed pi-subagents child planner preserves `~` in `subagentOnlyExtensions`; Pi's resource loader expands it. A disposable integration test against Pi 1.6.0 and the installed pi-subagents planner and loader selected the four tools without `bash`, inspected a committed range, and loaded exactly one provider both without ambient extensions (the foreground loader configuration) and with ambient plus an explicit provider (the background loader configuration). The latter also deduplicated a `~` symlink spelling against the ambient absolute path. This result is specific to the tested runtime and same underlying file; different copies can still conflict. If duplication occurs, arrange for both paths to resolve to the same file, or explicitly list the needed extensions with `extensions` to disable ambient loading (include other required providers). Foreground children still need an explicit provider path.

A second disposable integration test loaded the actual permission-mode extension with default and plan modes configured to deny a file path and allow `git_r_*`: `read` was blocked, while `git_r_diff` exposed the committed canary. It disabled the Bash OS sandbox in this fixture; the test does not establish kernel isolation. These are direct planner, loader and headless SDK checks, not actual foreground or detached child launches, model-driven reviews, or proof about a different version or project override. Verify the effective configuration in the intended environment.

The runtime integration probes are optional: set `PI_PACKAGE_DIR`, `PI_GIT_TOOLS_SUBAGENTS_ROOT`, and `PI_GIT_TOOLS_PERMISSION_MODES_ROOT` to installed package roots before running `just git-tools test`. Without them the relevant probes are skipped; the core Git tests still run. The probes use disposable settings, repositories and scratch directories, not live user configuration.
